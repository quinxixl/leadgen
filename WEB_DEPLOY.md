# Запуск веб-кабинета без приёма платежей

## Ответы через личный Telegram-аккаунт

В карточке Telegram-лида на сайте и в боте доступна кнопка «Ответить через Telegram».
Пользователь выбирает личное сообщение автору или ответ в исходной супергруппе,
вводит текст (до 3000 символов), проверяет получателя и подтверждает отправку.
AI-оффер можно скопировать и отредактировать перед подтверждением. Автоматической рассылки нет.

Используется личное подключение того, кто отправляет отклик, включая участников команды.
Новые ключи не нужны: используются существующие `TELEGRAM_API_ID`, `TELEGRAM_API_HASH`
и `TELEGRAM_SESSION_ENCRYPTION_KEY`. Подключение выполняется на сайте в разделе «Telegram».
Аккаунт должен иметь доступ к исходному сообщению. Личный отклик направляется автору
исходного сообщения, а не произвольному контакту из текста. Скрытые авторы, боты,
удалённые сообщения и комментарии к каналам не поддерживаются.

Миграция `20261005070330_telegram_replies.sql` включена в `python -m leadgen.web_migrate`;
существующий автообновлятор применяет её до запуска новых контейнеров.
Миграция только добавляет закрытую таблицу откликов. При откате кода таблицу сохраняйте:
она хранит историю и защиту от повторной отправки.

Подтверждение действует 15 минут. Перед отправкой заново проверяются доступ к лиду,
роль, подписка, аккаунт и получатель. Повторное подтверждение того же отклика не создаёт
нового сообщения. При обрыве связи или остановке процесса отклик остаётся с неопределённым
результатом / в отправке: сначала проверьте переписку в Telegram. Автоповтора нет.
Успешный отклик появляется в истории; начальные этапы сделки меняются на «Написали»,
а более поздние этапы сохраняются.

## Состояние версии

Ветка `codex/web-product` содержит работающий многопользовательский кабинет. Она не обновляет сервер на `main`.
Вход подтверждается существующим ботом. Кабинет и бот используют одни таблицы пользователей,
лидов, настроек, обратной связи и статусов. Проекты и история требуют новой миграции.

Работают: лендинг, вход, лента и карточки, поиск, статусы, сумма сделки, обратная связь,
заметки, напоминания в Telegram с сохранением в базе, личные Telegram-подключения с выбором групп,
история изменений из кабинета, история статусов из бота, три быстрых шаблона и три AI-оффера Groq
по запросу пользователя с отдельным профилем отклика для каждого проекта,
массовые действия, расширенная обратная связь, теги, API-токены чтения/записи,
подписанные HTTPS-webhook с очередью повторов, проекты с независимыми
фильтрами, отсутствие повторного уведомления между проектами, CSV/XLSX с фильтрами, отчёты за 7/30/90 дней, динамика лидов, качество источников,
результаты проектов и время до отметки «Написали»,
каталог источников, аналитика спроса по направлениям, времени и типу потребности,
а также просмотр диагностики администратором.

Командный режим включает пространства, роли владельца, администратора, менеджера и наблюдателя,
одноразовые приглашения, назначение ответственного по лиду, Telegram-уведомление назначенному
менеджеру и отчёт по распределённым лидам и заказам.

AI-офферы создаются моделью `openai/gpt-oss-120b` только после нажатия пользователя, сохраняются
в базе вместе с расходом токенов и не отправляются заказчику автоматически. При ошибке Groq остаются
доступны детерминированные шаблоны. Частота ограничена одним запросом за 10 секунд и суточным лимитом команды.
Ещё не входят в эту версию: AI-скоринг входящих сообщений, готовые коннекторы amoCRM/Bitrix24/Google Sheets,
ограниченный пробный период. Их нельзя рекламировать как доступные.
Текущий доступ бесплатный, без срока и платежей. На экранах нет неработающих кнопок этих функций.

## Адрес

Собственный домен не обязателен. Подойдёт технический HTTPS-адрес хостинга с обратным
прокси к порту 8000. На VPS такой адрес автоматически не появляется: нужен технический
адрес провайдера или отдельно настроенный постоянный HTTPS-прокси.
Обычный HTTP по IP для публичного входа не используйте: cookies защищены флагом Secure.
Не публикуйте базу данных, файл `.env` или Telegram-сессию.

## Настройки сервера

Сохраните резервную копию базы и текущий SHA перед переключением версии.
Используйте уже настроенный `DATABASE_URL` из `.env`.
Добавьте в `.env`:

```dotenv
WEB_SECRET_KEY=значение_сгенерированное_командой_ниже
TELEGRAM_BOT_USERNAME=имя_вашего_бота_без_символа_собаки
WEB_ALLOWED_HOSTS=ваш-технический-адрес,localhost,127.0.0.1
WEB_ADMIN_TELEGRAM_IDS=ваш_числовой_Telegram_ID
TELEGRAM_SESSION_ENCRYPTION_KEY=отдельный_ключ_шифрования_Fernet
GROQ_API_KEY=новый_ключ_из_консоли_Groq
GROQ_MODEL=openai/gpt-oss-120b
```

Дневные лимиты AI-откликов зависят от тарифа и задаются в `leadgen/billing.py`; `GROQ_DAILY_DRAFT_LIMIT` больше не используется.

Создать секрет:

```sh
python3 -c 'import secrets; print(secrets.token_urlsafe(48))'
```

Создать отдельный ключ шифрования Telegram-сессий:

```sh
python3 -c 'from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())'
```

Не меняйте этот ключ после подключения пользователей: старые сессии перестанут расшифровываться.
`TELEGRAM_API_ID` и `TELEGRAM_API_HASH` приложения также должны быть настроены на сервере.
Ключ Groq храните только в `.env` с правами `0600`. После изменения ключа перезапустите оба контейнера.

Не добавляйте протокол, путь или порт в `WEB_ALLOWED_HOSTS`. Telegram ID администратора
задаётся только окружением сервера; пользователь не может повысить свои права через сайт.

## Сборка и миграция

После проверки версии на тестовом окружении:

```sh
cd /opt/leadfinder
git fetch origin
git switch --track origin/codex/web-product
docker compose -f compose.yaml -f compose.web.yaml build
docker compose -f compose.yaml -f compose.web.yaml run --rm --no-deps leadfinder python -m leadgen.web_migrate
docker compose -f compose.yaml -f compose.web.yaml up -d
docker compose -f compose.yaml -f compose.web.yaml ps
curl -fsS http://127.0.0.1:8000/healthz
```

Миграцию запускайте этим способом. Не применяйте тот же SQL отдельно через панель Supabase:
повторный запуск должен видеть запись и контрольную сумму в `leadgen.web_schema_versions`.
Базовые миграции существующего бота должны быть применены заранее.
При ошибке миграции не запускайте новую версию бота: ей нужны таблицы проектов и истории.

Прокси должен передавать `X-Real-IP`, `X-Forwarded-For`, `X-Forwarded-Proto` и исходный `Host`, а также обслуживать HTTPS.
`X-Real-IP` нужен webhook ЮKassa: по нему проверяется, что уведомление пришло с адресов ЮKassa.
Приложение доверяет одному такому прокси. Порт 8000 должен оставаться привязанным только к localhost.
Если хостинг запускает web-контейнер отдельно, используйте команду из `compose.web.yaml`
и передайте переменные окружения. Сам бот должен оставаться постоянно работающим процессом.

## Публичный HTTPS

Для production-домена `signalid.ru` направьте A-записи `@` и `www` на выделенный
публичный IP сервера. Готовая конфигурация Nginx находится в
`deploy/nginx/signalid.ru.conf` (HTTPS, HTTP/2, gzip, статика без gunicorn, лимиты на вход и API).
Она ссылается на сертификат certbot, поэтому сначала выпустите его
(`sudo certbot certonly --nginx -d signalid.ru -d www.signalid.ru`), затем установите файл:

```sh
sudo install -m 0644 deploy/nginx/signalid.ru.conf /etc/nginx/sites-available/leadfinder
sudo ln -sf /etc/nginx/sites-available/leadfinder /etc/nginx/sites-enabled/leadfinder
sudo nginx -t
sudo systemctl reload nginx
```

Обновление уже работающего сервера, проверка и откат — в `DEPLOY.md`, раздел 17.

Для другого домена замените `server_name` в копии конфигурации. Эквивалентный пример прокси Nginx:

```nginx
server {
    listen 80;
    server_name leads.example.ru;
    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}
```

После проверки конфигурации выпустите сертификат командой
`sudo certbot --nginx -d leads.example.ru`. Замените адрес в примере на свой домен и добавьте его
в `WEB_ALLOWED_HOSTS`. Порт 8000 наружу не открывайте.

## Тарифы вручную (оплата не подключена)

Так сайт работает, пока в `.env` пуст `YOOKASSA_SECRET_KEY` (см. «Оплата через ЮKassa»). Выдача тарифа
из `/admin` и командой `set-plan` остаётся доступной и после подключения оплаты.

Кнопка «Подключить «Тариф»» в разделе «Подписка» (сайт и Mini App) создаёт заявку в `leadgen.plan_requests`
(одна открытая заявка на пользователя, повторное нажатие её обновляет) и присылает уведомление в
`FEEDBACK_CHAT_ID`, а если он пуст — в личные чаты `WEB_ADMIN_TELEGRAM_IDS`. В `/admin` («Заявки на тарифы»)
кнопка «Выдать» включает тариф на месяц или год и пишет пользователю в бот, «Отклонить» закрывает заявку.
Там же форма «Тариф пользователя»: любой тариф, срок (+1 месяц, +1 год, до конца беты, бессрочно, до даты)
и цена участника беты. Все изменения записываются в `leadgen.plan_changes`.

Администраторы (`WEB_ADMIN_TELEGRAM_IDS`) и служебные аккаунты (`UNLIMITED_TELEGRAM_IDS`) всегда работают на
тарифе «Команда» без срока — это вычисляется в коде, записи в базе не меняются.

Аварийно, без сайта:

```sh
sudo docker compose -f compose.yaml -f compose.web.yaml exec web python -m leadgen.billing set-plan --user @username --plan pro --months 1
sudo docker compose -f compose.yaml -f compose.web.yaml exec web python -m leadgen.billing set-plan --user 123456789 --plan team --forever
```

`--user` — внутренний id, Telegram ID или @username; срок — `--months N` (продлевает текущий срок того же
тарифа), `--until 2026-12-31` или `--forever`; `--founder on|off` включает или снимает цену участника беты.

## Оплата через ЮKassa

Оплата тарифов идёт через умный платёж ЮKassa: пользователь переходит на страницу ЮKassa, выбирает способ
оплаты и возвращается в кабинет. Тариф включается после HTTP-уведомления (webhook) от ЮKassa, а не по
возврату пользователя. Чеки формирует сервис «Чеки от ЮKassa» (продавец — ИП). При согласии пользователя
ЮKassa сохраняет способ оплаты, и подписка продлевается автоматически; данные карт у нас не хранятся.
Пока `YOOKASSA_SECRET_KEY` пуст, оплата выключена и работает ручная заявка на тариф.

### 1. Тестовый магазин

1. Зарегистрируйтесь в [личном кабинете ЮKassa](https://yookassa.ru/my) и создайте тестовый магазин
   (переключатель магазинов в шапке → «Тестовый магазин»). У тестового магазина свои `shopId`,
   ключи и настройки уведомлений; деньги не списываются.
2. В тестовом магазине: «Интеграция» → «Ключи API» → выпустите секретный ключ (`test_…`).
   `shopId` указан в том же разделе и в «Настройках магазина».

### 2. Ключи в `.env`

```dotenv
YOOKASSA_SHOP_ID=123456
YOOKASSA_SECRET_KEY=test_xxxxxxxxxxxxxxxx
# 1 — без НДС (УСН)
YOOKASSA_VAT_CODE=1
# необязательно: код системы налогообложения для чека
YOOKASSA_TAX_SYSTEM_CODE=
# сайт за nginx: IP клиента берётся из X-Real-IP
YOOKASSA_TRUST_PROXY=1
```

Секретный ключ храните только в `.env` с правами `0600`, не публикуйте в Git, чатах и логах.
После изменения перезапустите web-контейнер:

```sh
sudo docker compose -f compose.yaml -f compose.web.yaml up -d web
```

### 3. HTTP-уведомления (webhook)

В личном кабинете ЮKassa: «Интеграция» → «HTTP-уведомления». Укажите адрес

```text
https://<домен>/webhooks/yookassa
```

и отметьте события `payment.succeeded`, `payment.canceled` и `refund.succeeded`.
У тестового магазина уведомления настраиваются отдельно — повторите настройку в нём.
Адрес должен открываться по HTTPS с действительным сертификатом. Nginx из
`deploy/nginx/signalid.ru.conf` передаёт `X-Real-IP` и `X-Forwarded-For`; при своей конфигурации прокси
добавьте `proxy_set_header X-Real-IP $remote_addr;`, иначе уведомления будут отклоняться как пришедшие
не с адресов ЮKassa. Если прокси нет и сайт открыт напрямую, задайте `YOOKASSA_TRUST_PROXY=0`.

### 4. Таймер автопродления

Раз в час таймер запускает `python -m leadgen.payments renew` в web-контейнере: списывает оплату по
сохранённому способу у подписок, срок которых подходит к концу, и повторяет неуспешные списания.
Сервис работает не от root, а от пользователя `leadfinder-deploy`. Его создаёт
`deploy/install-auto-update.sh` (DEPLOY.md, раздел 14), поэтому сначала выполните установку автообновления.

```sh
cd /opt/leadfinder
sudo chmod 0755 deploy/leadfinder-renew.sh
sudo install -m 0644 deploy/leadfinder-renew.service /etc/systemd/system/leadfinder-renew.service
sudo install -m 0644 deploy/leadfinder-renew.timer /etc/systemd/system/leadfinder-renew.timer
sudo systemctl daemon-reload
sudo systemctl enable --now leadfinder-renew.timer
sudo systemctl list-timers leadfinder-renew.timer --no-pager
```

Проверить вручную и посмотреть журнал:

```sh
sudo systemctl start leadfinder-renew.service
sudo journalctl -u leadfinder-renew.service -n 100 --no-pager
```

Скрипт обращается к уже запущенному контейнеру `web` (`docker compose exec`). Если в момент запуска
автообновлятор пересоздаёт контейнеры, запуск завершится ошибкой, и списание выполнится через час.
Если проект лежит не в `/opt/leadfinder`, поправьте пути в `leadfinder-renew.service` до установки.

### 5. Тестовые карты

В тестовом магазине используйте любой будущий срок действия и любой CVC:

| Карта | Результат |
| --- | --- |
| `5555 5555 5555 4444` | успешная оплата без 3-D Secure |
| `5555 5555 5555 4477` | успешная оплата с 3-D Secure |
| `5555 5555 5555 4600` | отказ: недостаточно средств |

Для проверки автопродления сохраняйте карту без 3-D Secure (`5555 5555 5555 4444`): повторные списания
идут без участия пользователя, и карта с обязательным 3-D Secure их не пройдёт.
Проверьте: оплата включает тариф; отмена и отказ не меняют тариф; повторное уведомление не продлевает срок
дважды; отключение автопродления в разделе «Подписка» сохраняет оплаченный период; возврат из кабинета
ЮKassa приходит событием `refund.succeeded`; чек приходит на email.

### 6. Переход на боевой магазин

- [ ] В `.env` — `shopId` и ключ `live_…` боевого магазина; web-контейнер перезапущен.
- [ ] В боевом магазине настроены HTTP-уведомления на `https://<домен>/webhooks/yookassa`
      с событиями `payment.succeeded`, `payment.canceled`, `refund.succeeded`.
- [ ] Менеджер ЮKassa включил автоплатежи (сохранение способа оплаты) для боевого магазина — без этого
      рекуррентные списания отклоняются.
- [ ] Подключены «Чеки от ЮKassa»: заполнены данные ИП, система налогообложения и ставка НДС
      (`YOOKASSA_VAT_CODE=1` — без НДС на УСН).
- [ ] На сайте опубликована оферта (`/terms`) с разделом об автоматическом продлении; в `LEGAL_ENTITY`
      указаны реквизиты ИП.
- [ ] Установлен и активен `leadfinder-renew.timer`.
- [ ] Одна реальная оплата минимальной суммой прошла, тариф включился, чек пришёл; затем сделан возврат.

## Алерты об ошибках в Telegram

Основной канал оповещений: бот присылает владельцу короткое сообщение «🔴 Ошибка в web/bot» с типом
ошибки, компонентом, внутренним ID пользователя, коротким traceback (файл:строка функция), хостом и временем МСК.
Телефоны, email, токены, ключи и пароли из URL базы вычищаются до отправки.

1. С рабочего аккаунта Telegram откройте бота и отправьте `/start` (без этого Telegram не даст боту писать вам).
2. Узнайте свой числовой ID, например у @userinfobot.
3. Добавьте в `.env` и перезапустите контейнеры:

```dotenv
ERROR_ALERT_CHAT_ID=123456789
# необязательно: сообщение при каждом старте
ALERT_ON_START=0
```

Несколько получателей — через запятую. Пустое значение выключает алерты; на другие ID админов они не уходят.
Одинаковая ошибка (тип + место в коде) приходит не чаще раза в 10 минут, затем — с числом повторов;
всего не больше 20 алертов в час. Лимиты считаются в каждом процессе отдельно: у сайта несколько
gunicorn-воркеров, поэтому одна и та же ошибка может прийти по разу от каждого воркера.
Проверка (сообщит, какие каналы сработали — Telegram и/или Sentry):

```sh
sudo docker compose -f compose.yaml -f compose.web.yaml exec web python -m leadgen.observability --test
```

## Мониторинг ошибок (Sentry / GlitchTip)

Необязательно. Сайт и бот отправляют ошибки в Sentry или self-hosted GlitchTip, если в `.env` задан DSN:

```dotenv
SENTRY_DSN=https://ключ@glitchtip.example.ru/1
SENTRY_ENVIRONMENT=production
SENTRY_TRACES_SAMPLE_RATE=0
SENTRY_RELEASE=короткий_SHA_коммита
```

Пустой `SENTRY_DSN` полностью выключает отправку. Уходят необработанные ошибки Flask, падения бота,
сбои фоновых циклов (парсеры, AI-оценка, напоминания, уведомления) и логи уровня ERROR.
Тела запросов, cookies, заголовки авторизации и query-строки не отправляются; телефоны, email,
токены бота, ключи `gsk_…` и пароли в URL базы вычищаются. Из данных пользователя — только внутренний числовой ID.
После перезапуска контейнеров проверьте доставку (событие появится в проекте Sentry/GlitchTip):

```sh
sudo docker compose -f compose.yaml -f compose.web.yaml exec web python -m leadgen.observability --test
```

## Автообновления

Установите таймер с нужной веткой и поддержкой web-контейнера:

```sh
cd /opt/leadfinder
sudo env LEADFINDER_BRANCH=codex/web-product LEADFINDER_WEB=1 ./deploy/install-auto-update.sh
sudo systemctl status leadfinder-update.timer --no-pager
```

Обновлятор собирает образ, применяет миграции и только потом заменяет контейнеры.
Включайте ветку разработки только на тестовом сервере до завершения списка требований.
Рабочий сервер на `main` продолжает использовать текущую версию.
